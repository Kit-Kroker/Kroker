0. Why a benchmark is the load-bearing artifact BENCHMARK §0

Three independent sources converge on the same claim, and the factory’s own roadmap is the fourth.

Quality is a trajectory Abdullin

Start a project from the feedback loop, not the architecture. The eval environment is the instrument that lets you compare any architecture on your task in minutes. Half the work is building that environment and labelling the hard cases; the clean harness is a by-product of the eval, not the goal.

The harness is the variable Cursor · SQLite swarm

Hold the task, the models, and the time budget fixed; vary only the harness; grade against a held-out suite the swarm was never told existed. The behavioural differences (thrash, contention, duplicated work) were far larger than the score differences — so a single pass/fail number hides the thing you actually want to improve.

Model economics Cursor

Every model mix reached similar quality at wildly different cost — $1,339 → $10,565 on the same task — because few moments in a task need frontier intelligence. Cost per role, not per token, is the number that moves.

The factory’s own state ROADMAP §0 / SC-1..6

SC-1 through SC-6 are marked not measurable or mechanism-exists-no-metric. The pipeline can ship a feature end-to-end (P1 done), and the instrument that turns that into numbers is now mostly built: how cheaply is measurable per run via RunSummary.roles (E-33), and how well is measurable for Python cases via the held-out oracle (E-30/E-31). Cross-language coverage (E-30a/b/c) and the overfit anti-cheat (E-31a) stay open — the precondition for P3’s exit and everything in P4.

Design stance, carried from the architecture (ADR-11). ADR-11 already commits the factory to a deterministic DAG contra the Bitter Lesson. The benchmark inherits that stance: it is a fixed, versioned instrument, not a self-modifying one. The two feedback loops below improve the system under test; the instrument itself changes only through reviewed diffs — exactly as ADR-11 treats the DAG.

2. Ground truth — three tiers BENCHMARK §2 · cheapest → most objective

The factory builds greenfield features, so there is no back-catalogue of closed tickets to mine. Ground truth has to be authored, in three tiers. Every benchmark case declares which tier(s) grade it.

Tier A · objective, ungameable

Held-out acceptance tests

done (new scope)

The Cursor pattern: a test suite the factory is never told exists, run against the produced code, graded as fraction passing. Authored with the case; the gap between the factory's own criterion→test mapping and the hidden oracle is itself a signal.

  • Ground-truth artifact: benchmarks/cases/<case>/oracle/ — suite + fixtures, held out of the workflow's context, run in a clean checkout through the case's ToolchainAdapter (ADR-15). Landed (E-31): grade_oracle runs after each benchmark child via JUnit XML; cat-café + todo-api ship oracles.
  • Language by marker file in the produced repo (pyproject.toml / package.json / go.mod / Cargo.toml); manifest-vs-detected mismatch is itself a signal. Python reference only (E-30); Go/TS/Rust = E-30a/b/c.
  • Coverage → Cobertura XML; security floor → semgrep / SARIF; gate stays language-agnostic (ADR-15, E-30).
  • Anti-cheat (Cursor's manual review, made routine): (i) oracle-held-out assertion landed (E-31) + diff-coverage "built evenly" check open (E-31a); (ii) session inspection via HarnessSession (E-38) + the deep_review lens (E-39) — did the agent peek at a hidden test, hardcode answers, or fit to a discovered oracle? (new scope vs E-27)

Landed (E-30 + E-31): the coverage seam and the held-out oracle are wired end-to-end (Python) — the single highest-leverage fix in the whole document is done. E-31a (diff-coverage anti-cheat) and E-30a/b/c (other languages) remain — see §6.

Tier B · subjective, already built

Rubric judging

done — rubrics + calibration tracking

The E-27 mechanism: a rubric per stage, scored by the cross-family judge. The only way to grade non-code stages (clarify quality, architecture soundness, research grounding) where no oracle can exist. Already wired for clarifier / architect / planner and, since E-27, qa / research.

  • Calibration requirement (non-negotiable): before a rubric's score is trusted in a phase-exit decision, hand-score 20–30 fixtures and confirm judge agreement (report the agreement rate; low agreement = rubric defect, not model defect). Track per rubric. Landed (E-36 / FR-110): sdlc calibrate <rubric> reports within-epsilon agreement + MAE + Spearman, surfaced as a trust level beside every rubric score.
  • Known open defect: research grounding is unreachable for a mid-tier author model — verify_brief fails closed on byte-exact quote matching and glm-5.2 plateaus at 3 violations (E-29). Benchmark cells handle this decided in OQ-B3 (a grounding failure is a recorded research-stage FAIL; the run continues), so a cell's research grade is earnable but never a silently-unearnable number.
Tier C · differential

Golden-artifact regression

partial — on-demand half

ARCHITECTURE §10’s named mechanism: a committed baseline artifact per stage; a new run diffs against it; drift is a reviewed event, not a silent change. It does not say “how good” — it says “changed vs the known-good baseline”, which is exactly what you want for regression protection during prompt/model iteration.

  • sdlc eval (E-4) is the on-demand half; the committed-baseline + CI-check half is a named future increment (OQ-E2 in E-4’s note).
  • Use for: every prompt edit and model swap, as the fast inner loop.

Relationship to A/B: C catches “you made it different”; A/B catch “you made it worse”. C is cheap and runs on every change; A is expensive and runs on the matrix.

3.0 Language is a case property, not a fifth axis

Generated projects can be any language, but language should not be a sweep dimension crossed with the others (that multiplies the matrix for little insight). Instead each case declares its language and carries an oracle in it (§2 Tier A, E-31); the corpus spans several languages; and the error heatmap is sliceable by language (§4.4). This catches the real risk cheaply: if every prompt and rubric was tuned on Python cases, the factory may quietly do worse on Go, and a Python-only benchmark never sees it. The machinery that makes any of this work is the ToolchainAdapter (ADR-15) under E-30.

3.1 Harness axis — and where cursor fits

Adding cursor is worthwhile, but as a third point on this axis, not as a replacement. The value is not “cursor vs claude in the abstract” — that is a blog post about someone else’s task. The value is measuring claude -p vs opencode vs cursor on your SDLC, through your DeterministicQualityGate, on your held-out oracles. That comparison cannot be bought or borrowed.

Hard requirement (FR-203 + the HarnessRunResult contract): a new harness adapter must normalise its output — tokens, cost, context_window, compacted, session-resume handle — into HarnessRunResult. Landed (E-35, folds E-24): CursorHarness is registered in worker.py, normalising stream-json into HarnessRunResult; the version pin is declared (expected_version) but left None until a real cursor-agent --version can be captured, and cursor's total_cost_usd may be absent — so cursor cells can still be quality-only until the adapter sees real cost output.

3.2 Model × role — the economics result to reproduce

Cursor’s finding, restated for this factory: the expensive roles are the proposers that decide (architect on opus-4-8 per agents.yaml), and the volume is in the harness roles that execute. The benchmark should attribute dollars per role, not tokens, because planner-family tokens cost multiples of worker-family tokens — precisely Cursor’s $1,339-vs-$10,565 experiment, expressed in your config.

Landed (E-37, folds E-26): cfg.roles was a hardcoded mirror of agents.yaml because PipelineConfig() is constructed inside the workflow. The override now resolves at the boundary — each cell carries a named Arm (role→model mix), _cell_config builds cfg.roles from it, and validate_run_roles enforces ADR-6 per run; the CLI exposes the same override via --role-model. The full model×role sweep is now expressible (the pre-E-37 harness-only models=[...] form still works, desugared to one arm per model).

3.3 Memory axis — the measurement the whole stack was built for

This is the axis that justifies Hindsight’s presence, and it is the one the roadmap is furthest from being able to run. The experiment is simple: the same case, same models, same harness, run with memory.enabled=false and memory.enabled=true. The delta in quality (and fix-loop cost — recalled gotchas should make attempt N+1 cheaper) is the value of memory.

Why it still can't run fully, precisely: SC-4 ("repeat-clarification <10% by run 10") and SC-6 ("soft-gate override <5%") both need reflect wiring + real runs. The per-run signal now accrues — the retro stage (14, E-32) emits a RunSummary (carrying clarifications[].answered_by and gates[]) on every terminal path and calls reflect(project_bank) (gated on memory.enabled, default false). Still open: nothing writes to org_bank (E-25), so the cross-run aggregation into a run-10 series / override rate remains the benchmark's job. The memory axis is gated on that last step — §6's second priority.

4. Metrics — beyond a single pass rate BENCHMARK §4 · a row per run

Cursor’s central lesson: the behavioural differences dwarfed the score differences. A benchmark that emits one number per run cannot see thrash, duplicated work, or a harness that silently compacted mid-task. The factory should emit a row per run with the fields below, aggregated across the matrix.

4.1 Quality the grade

  • Oracle pass rate — fraction of the held-out Tier-A suite passing. The primary number. Requires §6 priority 1.
  • Grade-over-time — Cursor grade the suite as a rising curve; the factory’s stages are discrete, so the natural analogue is grade at each gate (post-clarify, post-architecture, post-plan, post-QA, post-merge): a step curve showing where quality is won or lost.
  • Rubric scores per stage (Tier B) — for non-code stages, with the calibration agreement rate attached so a score is never read without its trust level.
  • Traceability gap — criteria the factory tested (its own mapping) vs criteria the oracle covers. A proxy for “did it build evenly or to the test” (the Cursor anti-cheat, quantified).

4.2 Economics the cost

  • $ per run, decomposed per role (not per token — §3.2).
  • Tokens per role, with the planner/worker split Cursor highlight (workers carried ≥69%, often >90%, of tokens but a minority of cost).
  • Context-ceiling events — input_tokens > fraction × context_window and compacted=true counts, from HarnessRunResult (SDLC-spec §4, ADR-13). A harness that keeps hitting its ceiling is a signal to decompose smaller.

4.3 Coordination & waste factory analogue of swarm thrash

The factory runs a serial DAG, not a 1,000-commit/sec swarm, so Cursor’s merge-conflict/megafile metrics don’t port directly. The principle does: measure work that didn’t advance the goal.

  • Fix-loop attempts per run — QA loop (MAX_REPAIR_ATTEMPTS, spec 3) and review-fix loop (MAX_REVIEW_FIX_ATTEMPTS = 2). Record the actual cap in force — note the numeric drift (FR-105: default 2 vs spec 3).
  • Gate rounds per gate — REVISE re-entries (MAX_GATE_ROUNDS, default 2, FR-301).
  • Escalations — how often fix loops exhausted into a hard human gate.
  • Wall-clock per stage — from Temporal history, free.
  • Session-derived waste (from HarnessSession, E-38) — the richest signal the diff hides: tool-call count, file re-reads, failed commands (non-zero exits), and rewrite/backtrack churn within a run. The transcript shows “rewrote the auth module three times before settling”; the diff never does. Also surfaces compacted mid-run context loss (ADR-13) as what was dropped. Aggregates are computed pre-truncation, so they are kept on clean-green runs too (where only a SessionDigest survives) — the heatmap never goes blind on green. Landed 2026-08-03: WasteBag on BenchmarkRecord + benchmarks/waste_matrix.py — six gridded metrics in a task × arm grid (coding tasks only; proposer stages have no transcript by construction); volume metrics and compacted ride on the record without a grid.

4.4 The error heatmap Abdullin’s prioritisation instrument

Aggregate the above — including the session-derived waste (§4.3) and the anti-cheat findings — into a case × stage grid: rows are benchmark cases, columns are the 15 stages, cell colour is failure/rework density (gate rejections, fix-loop iterations, oracle failures attributable to that stage).

This answers the only question that matters between iterations: which stage, on which class of case, is costing the most — and therefore what do I fix next. It is strictly more useful than a scalar and it is the natural home for every §4.1–4.3 metric.

Landed 2026-08-03. The case × stage heatmap is one of five grids written by sdlc benchmark score — heatmap, task-matrix, error-matrix, waste-matrix, sc-rollup (cross-run SC-1/3/4/6) — each emitted as {.html,.json} into the score directory by re-scoring stored evidence in seconds. A sixth grid, agreement_matrix, carries the adversary lens separately (see below).

New measurement lens — the adversary arm + agreement_matrix. The adversary role is an optional second reviewer on the approve path (it runs only when the primary reviewer approves, so it is pointed at the expensive false-approve failure mode), off by default (adversarial_review_enabled). In the benchmark it is swept as an ARM — on vs off — and compared on held-out oracle pass-fraction against cost. The dedicated benchmarks/agreement_matrix.py grid reports split rate (adversary FAIL ÷ all adversary records) + cost per split per task × harness#model arm, descriptively; a record with no adversary contributes no cell (no zero cell). What it deliberately cannot tell you is whether the adversary was right — that is the ARM comparison (adversary-on vs adversary-off on the held-out oracle), not a cell value. On a split the run fails and the fix loop receives the union of both reviewers’ findings.

5. Cases — authoring the corpus BENCHMARK §5 · the dataset

Cases are the dataset. Three sources, matching the greenfield reality (there is no history to mine):

Spec-authored katas primary

A case is a feature spec + a held-out oracle suite, authored together. The bar E-27 set is the right one: “large enough to require decomposition and small enough to specify completely.”

Closed (E-34): cat-café now freezes an interface contract (ASGI app:app, /telemetry, /floorplan, /cats) and ships a held-out oracle/ (language: python), validated in CI against a reference impl (tests/fixtures/cat_cafe_ref/). The decomposition-forcing kata — the load-bearing variable Cursor's entire result turns on — is finally graded.

Public anchors external validity

A handful of SWE-bench-Verified-style tasks (issue → PR with hidden tests) give an external, task-independent reference point that doesn’t move when you change your own prompts.

Use them to tell “my change regressed my cases” from “my change regressed everything”. These grade purely on Tier A.

Distilled production incidents loop B

Abdullin’s loop B and Cursor’s Field Guide are the same idea: every time the factory fails in real use, that failure becomes a case. This is the mechanism that grows the corpus past the cold start — and it is exactly what the retro stage (14) + RunSummary are for.

The retro stage (§6 priority 2) now runs (E-32), but the loop-B intake still needs an org_bank writer (E-25) to consolidate across runs; until then, cases are hand-authored only.

Field Guide vs Hindsight — a note, not a task. Cursor’s Field Guide (a line-budgeted, agent-curated index.md injected at every agent start) is a lightweight, in-repo cousin of Hindsight’s cross-run memory. It is worth holding as a fourth memory-axis condition eventually (none / Field-Guide / Hindsight-project / Hindsight+org), because it isolates “shared scratchpad within a run” from “consolidated memory across runs” — but it is speculative and should be filed, not scheduled, in the spirit of E-5.

7. Open questions BENCHMARK §7 · OQ-B1..B10

OQ-B1
Oracle authorship cost.
Tier-A oracles are hand-written per case. What is the minimum corpus (how many cases, what complexity spread) before the matrix produces a trustworthy signal rather than noise? Cursor ran one task across four mixes; Abdullin spent half a project on the environment. Likely 10–30 cases, but this needs its own calibration.
OQ-B2
Judge independence under model sweep → E-37 — ANSWERED 2026-07-24.
ADR-6 forbids the judge sharing a family with the producer. Resolution: the judge is fixed per case (one judge_model on CaseSpec), and expand_matrix validates at expansion that its family differs from every producer model in every arm — so a case whose judge collides with any arm's producer family is rejected before any cell runs. 8. Judge sensitivity (E-83) BENCHMARK §7 · judge & plan-adherence

E-83 sharpened the quality instrument and added the one plan-execution signal the pipeline did not measure. Quality scores from before and after E-83 sit on different scales; the judge field on each record makes the boundary queryable (records now carry judge="staged_rubric"; pre-E-83 records keep "llm_judge"), and report.md names it — so averaging across the boundary is now visible, not implicit.

Typed rubric vetoes src/sdlc/benchmarks/vetoes.py

A rubric criterion that states an absolute override (“scores 0 regardless”) is a closed three-kind vocabulary — mentions_all / not_both / nonempty — evaluated deterministically over the parsed artifact, zero model calls, at both layers: an ABSOLUTE failure in the prompt gate, and a forced 0.0 override at Layer 3.

  • Authored per case as benchmarks/cases/<case>/vetoes-*.yaml.
  • Word boundaries, not substrings — the mentions_all matcher was corrected during the E-83 review to match on word boundaries, so a veto on scope no longer fires on telescope.

Staged judge two calls, cached steps

The single-shot rubric prompt became two calls: rubric → ordered evaluation steps (cached per sha256(rubric)), then artifact → per-component scores.

  • Vetoes override the LLM’s output rather than being argued into it — the model never has to concede a veto; the veto is applied on top.
  • The judge-never-raises invariant was restored in _judge_sync — a rubric that the model mis-formats is contained, never an unhandled exception.
  • Records carry judge="staged_rubric"; pre-E-83 records keep "llm_judge".

Plan adherence, split by provenance the missing plan-execution signal

Two signals, deliberately split by how they are produced:

  • Deterministic PlanDrift on each code-stage BenchmarkRecord — files_hinted vs files_touched, with hinted_untouched / touched_unhinted counters. No model in the loop.
  • Advisory plan_deviations folded into the existing deep_review lens (E-39) — not a fifth lens; each deviation carries verbatim transcript evidence or is dropped.

Sensitivity is proven, not asserted mutation suite

The mutation suite (SDLC_PROMPT_EVAL=1 python -m pytest -m prompt_eval -k mutations) records what real model behavior does to degraded prompts.

  • scope_dropped fails absolutely via the scope_preserved veto — the gate’s teeth are real and end-to-end, now that the veto matcher uses word boundaries.
  • truncated remains the open case — it has no veto and relies on the advisory judge, so it is not yet an absolute failure. See spec §9 for the recorded outcome.
