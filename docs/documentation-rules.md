# Documentation Rules

Conventions for authoring and maintaining documentation in this repository.
Every agent and human contributor writing or editing documentation here is
bound by these rules.

## Three documents, one job each

Every unit of code (a vertical slice under `src/sdlc/stages/<stage>/`, or a
component under `interfaces/ui/src/components/<name>/`) has three
co-located documents with non-overlapping purposes. They do not collapse:

| Document | Question | Audience | Lifetime |
|---|---|---|---|
| `<stage>.md` | **WHAT** — the functional contract, as numbered clauses | Anyone reading what the stage promises | Evergreen product specification |
| `AGENTS.md` | **HOW** — local invariants, framework traps, and test commands | An agent about to edit this slice | Tied to current harness tooling |
| Module docstring | **WHY** — design choices, rejected alternatives, security posture | Anyone reading the source code | Lives directly with the code |

Collapsing `<stage>.md` and `AGENTS.md` is a common temptation that breaks
durability: `<stage>.md` describes evergreen pipeline behavior, while
`AGENTS.md` carries tool-specific guardrails and harness hints that change as
agent capabilities evolve.

**An `AGENTS.md` that has grown into a restatement of its `<stage>.md` is a defect.**

For module docstrings, `src/sdlc/dashboard/api.py:1-16` is the model docstring:
it explains why the module sits under `src/` rather than `interfaces/` (importability
under `pyproject.toml`), why there are three write routes rather than five
(domain signals collapse), and where its unauthenticated security posture stops
being acceptable (`E-60/FR-1004`). It explains *why* the code was built this
way, not merely what the syntax does.

## What lives where

The `docs/` directory is organised by durability rather than topic or chronology:

| Directory / File | Durability rule | Description |
|---|---|---|
| `docs/documentation-rules.md` | Living | Authoring standards and documentation architecture (this file). |
| `docs/framework.md` | Living | The framework contract: Temporal rules, `StageContext`, and activity registration. |
| `docs/features/` | Living (`main`) | Cross-DAG narrative area documents (`<area>.md`) and area guidance (`AGENTS.md`). |
| `docs/modes/` | Living | Methodology guides for common engineering tasks (e.g. `slice-migration.md`). |
| `docs/roadmap/` | Living (`main`) | Per-epic group detail files (`<group>.md`) split from `ROADMAP.md`. |
| `docs/reference/` | Maintained | Durable technical references (`foundation.md`, etc.) maintained when stale. |
| `docs/reports/` | Immutable snapshot | Dated one-offs (`<YYYY-MM-DD>-<topic>.md`), true when written, never updated. |
| `docs/schemas/` | Generated | HTML schema visualisations. Regenerated by scripts (e.g. `scripts/aggregate_benchmarks.py` generates `benchmark-analysis.html`). |
| `docs/superpowers/specs/` | Write-once | Historical design specs. Never updated after landing. |
| `docs/superpowers/plans/` | Write-once | Historical implementation plans. Never updated after landing. |
| `docs/superpowers/reviews/` | Write-once | Historical review records. Never updated after landing. |
| `docs/templates/` | Living | Canonical templates for `<stage>.md` and slice-level `AGENTS.md`. |
| `interfaces/ui/src/components/<name>/<name>.md` | Living (with code) | UI component clause contracts (WHAT) — the `docs/` triad's first member, co-located with the component instead of under `docs/`; same for `src/tokens/tokens.md` and the assembled-console clauses at `interfaces/ui/app.md`. |

The durability split settles maintenance arguments:
- If a document goes stale and should be updated to reflect reality, it belongs in `reference/` or the appropriate living folder.
- If a document is a dated diagnostic snapshot or audit of past state, it belongs in `reports/` and is never touched again.
- Files under `docs/superpowers/**` are historical records describing the tree on the day they were written. When a file moves in the tree, old references in `docs/superpowers/**` are deliberately left untouched.

## ARCHITECTURE.md and ROADMAP.md describe main only

`ARCHITECTURE.md` and `ROADMAP.md` are living documents that reflect only what
has actually landed on `main`.

In-flight work, speculative designs, and planned migrations live in their
respective design doc under `docs/superpowers/specs/` until their implementation
is merged.

Corollary: **a design spec is not documentation of the system; it is a record of
a decision.** No document or agent should cite a design spec under
`docs/superpowers/specs/` as evidence of current system behaviour.

## agents/ is not AGENTS.md

Do not confuse the `agents/` directory with `AGENTS.md` files:
- `agents/` (`agents/registry.yaml` and subdirectories `agents/<role>/instructions.md`)
  is a **product concept**: the runtime role registry loaded by `src/sdlc/agents/loader.py`
  to configure LLM prompts and role definitions during workflow execution.
- `AGENTS.md` files are **instructions for the assistant editing this repository**.

Editing `agents/<role>/instructions.md` changes product behavior, not your
instructions. Conversely, editing `AGENTS.md` sets rules for coding assistants
editing the repository. Adding `AGENTS.md` files throughout makes this more
confusable, not less.

## Documents move with their code

Co-located documentation (`<stage>.md`, `stages/<stage>/AGENTS.md`, and module
docstrings) must change in the very same commit as the code changes that affect
them.

A co-located document that was not updated in a diff changing its module's
behaviour is a review finding, not an oversight to defer. This is the artifact
boundary from the root `AGENTS.md`: code without a clause and a clause without
code are both defects.

## The root AGENTS.md is a router

The root `AGENTS.md` is a router, not an encyclopedia. It indexes where things
live, which commands to run, which binding rules apply, and where deep context
resides. It must never inline a stage's contracts, schemas, or business logic.

**Ceiling: 250 physical lines.** This is a strict ceiling far below the
repo-wide 1000-line ceiling.

Reason: an unbounded instruction file spends context budget on every single agent
turn and flattens everything it holds to uniform priority. When fifty rules sit
in one file, the single rule that mattered reads like the forty-nine that did
not. The stage migration table in `AGENTS.md` is the model to copy: concise
paths and statuses pointing outward to authoritative details.

## What we write down, and which question each answers

Three authored artifacts answer three distinct questions:

| Artifact | Question answered | Authority |
|---|---|---|
| Design spec (`docs/superpowers/specs/`) | What we **intend** | Explains intent at the time of design |
| Numbered clauses (`stages/<stage>/<stage>.md`) | What **behaviour** matters | Contract of observed, required behavior |
| Test suite (`tests/`) | What we **verify** | Executable check ensuring behavior holds |

A spec describes a system as someone intended it to be. A system that exists is
defined by what it does, and much of what it does is load-bearing precisely
because nobody explicitly designed it. Numbered clauses capture verified
behaviour, which is why clauses live with the code while specs remain historical
records.

A fourth question — *what actually happened* during an agent's run on this repo
— has no formal artifact yet and is deferred.

**The Product vs Harness Boundary:**
Kroker the product implements telemetry, evals, and golden benchmark cases for
the pipelines it executes against *other* repositories (`src/sdlc/observability/`,
`src/sdlc/eval/`, `benchmarks/cases/`). Those are product features.
This repository's own development harness — the environment agents work in when
editing Kroker — is entirely separate.
The boundary runs strictly both ways:
1. Nothing about how we develop this repository is ever added to `src/sdlc/` as
   product functionality.
2. The product's own runtime machinery is not silently repurposed as our
   development tooling.

## Language and register

- **Language:** All repository documentation is written in English.
- **Register:** Prose over bullet lists where reasons, rationale, or mechanisms
  are explained. Bullet lists are for enumerations of independent items.
- **Anchoring:** Anchor claims to real files and line numbers (`file:line`),
  enabling any reader or automated tool to verify the assertion.
- **Tone:** Factual, present-tense, and descriptive of reality. Never make
  aspirational statements ("this will soon do X") in living documents.
